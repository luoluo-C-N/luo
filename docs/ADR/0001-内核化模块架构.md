# ADR-0001：采用内核化模块架构，禁止在 prototype.js 上继续加功能

- **日期**：2026-09-08
- **状态**：已接受
- **决策者**：项目所有者
- **相关**：`架构设计-v1.0.md` §1 §2、`功能设计-v1.0.md` §1

---

## 背景

`src/prototype.js` 单文件 3,553 行，占 `src/` 的 92.4%，是 220KB 单文件 HTML 原型经 `tools/split-latest.mjs` 机械拆分的产物。已确认的具体问题：

| 问题 | 后果 |
|---|---|
| 全局命名污染（`var API_BASE`、`window.jumpTab` 等） | 功能加到第 N 个必撞名 |
| 样式无隔离（共用 626 行 `prototype.css`） | 一模块的 `.card` 污染另一模块 |
| 页面硬编码（`index.html` 777 行写死 5 Tab + 17 子页） | 每加功能改一次，越改越脆 |
| 无模块生命周期 | 单模块报错 → **整 App 白屏**（当前 P0 正是此形态） |
| 约 20 处硬编码 `http://localhost:8000` | 真机请求全部失效 |

由此被迫制定「单一写者原则」——本质是用纪律弥补架构缺陷。

## 决策

采用 `架构设计-v1.0.md` 定义的内核化模块架构：

- 内核只做四件事：注册 / 路由 / 能力 / 安全，永不写业务代码
- 一切功能皆模块，模块间禁止直接 import，只通过 `ctx` 能力 API 与事件总线通信
- 故障隔离：单模块崩溃只降级该模块
- 敏感数据走 vault 加密地基

**并冻结旧代码**：`prototype.js` / `index.html` 禁止再添加业务逻辑，现有功能按领域迁入 `modules/site/`。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 在 prototype.js 上继续加功能 | 0.01 已证明：16 小时高强度交付后，新增能力成本急剧上升，且无法并行 |
| 引入 React/Vue 重写 | 需重做全部手势与毛玻璃视觉；现有视觉是已验证资产，重写风险与成本不对称 |
| Flutter / React Native | 同上；且会失去 PWA 与桌面预览能力（design-0.01.md §选型已否决） |
| 仅做文件拆分不改架构 | 不解决命名污染、样式冲突与故障隔离，只是把一个大文件变成多个仍互相依赖的文件 |

## 理由

1. **架构 §2 原则 1 是可验证的判断标准**：新需求若让内核改动，说明设计错了。这比任何"代码要整洁"的口号都可执行。
2. **故障隔离是当前 P0 的直接解**。白屏 = 脚本一次性同步执行、无边界。模块化后至少降级而非崩溃。
3. **"单一写者原则"应由架构消除，而非由纪律维持**。拆到单文件 ≤300 行后自然可并行。

## 代价与风险

- 迁移期双轨并存，认知负担翻倍 → 按面板/模块灰度，同时只维护一条主链路（R8）
- 内核设计若把握不住，容易膨胀 → 内核改动强制 review 并说明"为何不能由模块实现"（架构 §14.3）
- 迁移可能引入视觉回退 → UI 令牌快照测试 + 并排截图比对（R7）

## 验收方式

- 单模块 `mount()` 抛错时，其余模块与导航仍可用（故障隔离回归测试）
- 新增一个模块**未改动 `src/core/` 任何文件**
- `grep -c "localhost:8000" src/` = 0
